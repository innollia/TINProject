# Kit 개발 계약

이 문서는 TINProject에서 장르 Kit를 계획·구현·검수하는 단일 작업 계약이다.

먼저 읽기:
1. `CONTEXT.md`
2. `PROJECT_DECISIONS.md`
3. `docs/DESIGN_PHILOSOPHY.md`
4. `docs/VISUAL_DIRECTION.md`
5. `docs/IMAGE_ASSET_WORKFLOW.md`
6. `docs/UI_WORKFLOW.md`
7. `docs/UI_IMPLEMENTATION_RULES.md` — UI 구현·수정·검수 시 필수
8. 해당 `plans/kits/*.md`

## 1. 목적

Kit는 **한 게임 안에서 장르를 바꿀 때 곧바로 꺼내 쓸 수 있도록 미리 만든 장르 시스템**이다.

목표는 많은 모듈 수가 아니다. 목표는 다음이다.

- 특정 장르의 핵심 시스템이 실제로 작동한다.
- 그 장르의 화면·입력·피드백 문법이 실제 게임처럼 읽힌다.
- 콘텐츠를 추가할 때 핵심 시스템 코드를 다시 설계하지 않는다.
- Reference Game을 사용자가 직접 플레이해 검토할 수 있다.
- 이후 TINProject의 실제 구간에 맞게 내용과 미술을 뜯어고치기 쉽다.

## 2. Primary Reference — 하나만 둔다

Kit마다 Primary Reference는 정확히 하나다.

허용:
- 인기 itch.io 게임
- 게임잼 또는 시간 제한 개발 대회 출품작
- 상용/출시 인디게임
- 실제 화면과 플레이 흐름을 충분히 확인할 수 있는 다른 완성 게임

금지:
- “Baba + Golden Idol + Persona 느낌”
- 여러 레퍼런스의 장점을 알아서 섞기
- 작품명만 적고 기억으로 구현
- 레퍼런스가 없는 상태에서 “게임답게” 자율 해석

### 조사 역할과 출처

UI의 실제 화면 자료는 사용자가 촬영한 스크린샷을 우선 기준으로 삼는다. 에이전트는 먼저 필요한 화면 상태와 촬영 목적을 구체적인 목록으로 만들고, 받은 스크린샷을 분석한다. 사용자에게 게임 규칙 조사까지 넘기지 않는다. 정지 화면으로 알 수 없는 모션·소리·입력 반복은 별도 동작 증거가 필요하다고 구분한다.

오브젝트·단어·속성·문법의 조사 범위는 팬덤 위키·나무위키 등의 전체 목록과 분류에서 먼저 파악한다. 공식 업데이트 노트는 추가·변경 사항을 확인하는 자료이며 전체 목록을 대신하지 않는다. 분류별 목록, 개별 항목 출처, 버전 차이, 조사 여부를 남겨 누락을 확인할 수 있게 한다. 접근하지 못한 항목은 미확인으로 표시한다.

출처가 설명하는 규칙은 출처를 붙여 보고서에 기록한다. 모든 위키 항목의 직접 재현을 조사 완료 조건으로 삼지 않는다. 출처 간 충돌, 설명이 불명확한 처리 순서, 구현에 중대한 경계 사례를 추가 조사·실험 대상으로 좁힌다.

원작의 이동·충돌·undo 등 조사로 확인할 수 있는 문법은 사용자 선택 질문으로 바꾸지 않는다. 전체 목록을 조사하기 전에 기존 구현이나 짧은 Reference Game 분량에 맞춰 원작의 핵심 문법을 축소하지 않는다.

### 상태별 증거

계획서에는 최소한 다음 상태의 실제 레퍼런스 출처를 기록한다.

- 첫 플레이 화면
- 평상시 플레이
- 선택/focus 또는 직접 조작 상태
- 핵심 시스템 변화 직후
- 실패/불가
- 성공/완료
- 메뉴/상세 화면이 핵심 문법에 포함된다면 해당 상태
- 장면/레벨 전환

각 출처 옆에는 **무엇을 따라갈지**를 적는다.

예:
- 보드 셀 비율
- 카메라 거리
- 오브젝트 밀도
- HUD가 없는 범위
- 선택 표시 위치
- 정보 공개 순서
- 입력 후 피드백
- undo/reset 접근 방식

실제 화면을 확인하지 못하면 계획이 미완성이다.

## 3. Reference Game — 10분 이상

모든 Kit는 최소 10분 이상 플레이 가능한 Reference Game을 가진다.

10분은 대기시간·걷기거리·반복 노가다로 채우지 않는다. **같은 Kit 시스템에 서로 다른 Authored Content를 여러 번 넣어보는 시간**이어야 한다.

계획서는 장르에 맞는 콘텐츠 단위를 먼저 정의한다.

예:
- 규칙 퍼즐: 여러 레벨
- FPS: 여러 전투/공간/무기 조합
- 추리: 여러 조사 장면과 추론 단계
- 어드벤처: 여러 장소/NPC/아이템/사건
- 클리커: 여러 규칙 변화/생산 단계

완료 시 최소 두 개 이상의 서로 다른 authored 단위가 같은 시스템을 재사용해야 한다. 장르 특성상 두 단위가 부적절하면 계획서에서 더 강한 하드코딩 검증 방법을 정의한다.

## 4. 콘텐츠 확장성

기본 목표는 **전용 에디터 없이 에이전트가 데이터/Resource/씬을 추가해서 콘텐츠를 늘리는 것**이다.

새 콘텐츠 추가에 허용:
- Resource
- JSON/Dictionary 등 계획에 명시한 데이터
- scene
- module-local asset
- authored script가 실제 콘텐츠 동작 자체인 장르에서의 작은 content script

새 콘텐츠 추가 때문에 반복적으로 고치면 실패:
- parser/evaluator
- movement/combat core
- save codec
- input routing
- 공통 상태 모델
- 레벨 로더/registry의 기본 알고리즘

전용 에디터 도구는 Kit 완료조건이 아니다.

## 5. 시스템/표현 경계

게임 상태가 진실이고 화면은 그 상태의 표현이다.

계획서는 최소한 다음을 분리한다.

- domain state
- rules/system
- authored content
- presentation
- input intent
- save/load
- transition

프레젠테이션 노드가 게임 규칙을 소유하거나, 화면 Label/ColorRect 상태를 읽어 판정하면 실패다.

## 6. UI와 HUD

기본값은 **아무것도 띄우지 않는 것**이다.

상시 HUD를 추가하려면 Primary Reference와 게임 상태상 항상 알아야 하는 정보라는 근거가 계획서에 있어야 한다.

금지:
- 공간명/자동저장/키설명 상시 HUD
- 우상단 Menu/Journal 버튼
- 개발 툴바 같은 버튼 행
- 디버그 상태 문자열의 release 노출
- 조작법 장문 overlay
- “무엇을 눌러야 하는지”를 화면 중앙 설명문으로 해결

Shell UI는 호출 전까지 화면에 존재감이 0이어야 한다. Esc 메뉴는 Esc를 눌렀을 때만 보인다.

## 7. Input Bubble

새 장르 구간에서 필요한 물리 키 집합이 달라질 때 Input Bubble 전환을 사용한다.

가상 격자의 각 셀은 물리 키 하나와 안정적으로 대응한다.

상태:
- `intact`: 온전한 뽁뽁이
- `popped`: 터진 흔적
- `rising`: 새 키가 아래에서 자기 셀로 올라오는 중
- `restoring`: 이전에 터진 키가 다음 구간에서 다시 필요해 복구되는 중

규칙:
1. 첫 장르 진입 전에 필요한 키가 `rising → intact`.
2. 플레이어가 실제 해당 키를 누르면 그 방울이 터진다.
3. 다음 장르 전환에서 **계속/다시 필요한 기존 키**는 `popped → restoring → intact`.
4. **새로 필요한 키**는 `rising → intact`.
5. **다음 장르에 필요 없는 키**는 `popped` 흔적으로 남는다.
6. 설명문으로 키 기능을 해설하지 않는다.
7. 키 리바인딩이 있는 경우 보이는 문자는 실제 현재 바인딩을 따른다.

예:
- Game A: `W A S D Z`
- Game B: `W A S D Z X`
- Game C: `W`

흐름:
- 시작창 A: WASDZ가 올라와 정착 → 누르면 각각 터짐
- 중간창 AB: 터졌던 WASDZ가 복구되는 동안 X가 새로 올라옴
- 중간창 BC: W만 복구되고 ASDZX는 터진 흔적으로 남음

움직이는 무늬 배경과 가상 격자 위에서 동작한다. 별도 튜토리얼 문장으로 목적을 설명하지 않는다.

## 8. 시각 자산

과거 at-icons 조립 기반의 문서·도구·실험은 `archive/icon_based_image_assets/`에 보관한다. 이미 만들어진 이미지 파일은 기존 경로와 내용 그대로 유지한다. 새 이미지 자산은 `docs/VISUAL_DIRECTION.md`의 개인 화풍 코어 + 프로젝트 아트 층, 자산군 Gold Standard, 생성·후처리 경계를 따른다. Kit 계획에는 사용할 레퍼런스, 자산군, 생성·편집 방식, 라이선스 범위를 명시한다.

Primary Reference의 **가독성·실루엣·밀도·레이아웃**은 따라가되 원작 자산은 복제하지 않는다.

### Kit별 톤앤매너와 이미지 제작 명세

Kit 계획의 Presentation에는 해당 Reference Game에서 실제로 제작할 이미지의 **톤앤매너**와 **이미지 제작 명세**를 포함한다. 자산이 많거나 장면별 연속성 규칙이 길면 `plans/kits/` 아래 별도 시각 명세 문서로 분리하고 계획서에서 링크한다. 별도 문서도 계획서의 일부이며 구현 전에 완성해야 한다. 해당 Kit가 쓰지 않는 자산군 문서는 만들지 않는다.

최소 내용:

1. 프로젝트 아트 층: 세계·시대·재질·색 관계·조명·형태·정서, 공통 개인 화풍 코어와의 적용 관계. Primary Reference에서 가져올 화면 문법과 복제하지 않을 고유 요소를 구분한다.
2. 화면별 정보 구조: 카메라·플레이 영역·오브젝트 밀도·배경의 정보 중요도. 플레이에 필요한 시각 단서는 원경/확대 상태와 비교 대상을 명시한다.
3. 자산 목록과 제작 단위: 인물, 환경, 게임플레이 스프라이트, UI, 조사화면 등 실제 필요한 자산군별 ID·용도·상태·재등장 관계. 생성하지 않을 자산도 출처와 사용 방법을 적는다.
4. 자산군별 생성 brief: 입력할 코어·프로젝트 층·해당 장면/인물/오브젝트 정본·활성 Gold Standard, 유지/변경 요소, 출력 크기·형식·알파·피벗·레이어, 금지 요소, 생성 또는 편집 방법.
5. 정확해야 하는 글자·숫자·기호와 비교 단서는 생성 이미지 안에 맡길지, 별도 텍스트/레이어로 합성할지 명시한다. 추리 정답에 영향을 주는 내용은 생성 결과를 실제 확대/게임 화면에서 대조할 방법을 적는다.
6. 후처리와 검수: 허용된 기계적 후처리, 출처·권리 기록, 하드 게이트, 720p/FHD/QHD 실제 화면 판정, 사용자 승인 지점.

장면별 사건·인물·공간·단서가 복잡한 Kit는 `docs/golden_idol_story/`의 13A~13G처럼 정체성, 공간, 카메라, 비교 단서, 문서 서식, 생성 전후 감사를 나눠도 된다. 이 형식과 분량을 모든 Kit에 강제하지 않는다. Golden Idol 문서의 사건 내용과 프로젝트 색·모티프는 다른 Kit의 제작 입력으로 가져오지 않는다.

생성 요청을 실행할 때는 `docs/IMAGE_ASSET_WORKFLOW.md`에 따라 필요한 정본을 매번 직접 첨부한다. 핵심 입력 문서나 링크를 읽을 수 없어 자산의 내용이 불분명하면 생성하지 않고 그 누락을 기록한다.

## 9. 해상도

필수 검수:
- 1280×720
- 1920×1080
- 2560×1440

세 해상도에서 핵심 플레이와 메뉴가 잘리거나 겹치지 않아야 한다.

고정 논리 viewport를 사용할 수 있지만 실제 출력은 세 해상도에서 검수한다. UI는 Container/anchor를 우선하고, 월드 격자처럼 의도된 고정 배치는 별도 계산으로 다룬다.

## 10. 공유 추상화

두 실제 Kit/화면에서 같은 의미와 계약이 확인되기 전에는 shared로 올리지 않는다.

두 번째 사용처가 확인되면 중복을 유지하는 대신 작은 공통 단위 추출을 검토한다. Kit 전체를 안정된 공개 프레임워크 API로 만들지 않는다.

기존 AppRoot + ModuleDirector + ModuleContext 방향을 유지한다. TINProject 밖으로 복사/포크하는 것을 기본 사용법으로 설계하지 않는다.

## 11. 구현 계획서 필수 항목

계획서에 빈칸이 있으면 구현하지 않는다.

1. Kit 목적
2. Primary Reference 하나
3. 실제 레퍼런스 화면/플레이 출처
4. 복제할 시스템/UX와 복제하지 않을 고유 콘텐츠
5. Reference Game의 10분+ 플레이 흐름
6. Authored Content 단위와 추가 방법
7. domain/state/data model
8. 핵심 시스템과 처리 순서
9. input actions
10. save/load/reset/undo 등 장르별 복구
11. presentation 구조
12. Kit별 톤앤매너·자산 목록·이미지 생성 brief·출처·제작 방식·라이선스·검수 계획
13. 화면별 상태
14. 실패/불가/성공 상태
15. 720p/FHD/QHD 검수
16. 자동 테스트
17. 수동 플레이 과제
18. 하드코딩 탐지 조건
19. 금지 shortcut
20. 완료 증거

“알아서”, “적당히”, “게임답게”, “레퍼런스 느낌으로”는 구현 지시로 인정하지 않는다.

## 12. 완료 판정

자동 테스트는 기능 정확성을 증명할 뿐 Kit 완료를 선언하지 않는다.

완료에는 모두 필요하다.

- Reference Game 10분+ 실제 플레이 가능
- Primary Reference의 핵심 시스템/UX 문법이 화면에서 읽힘
- 여러 Authored Content가 같은 core를 재사용
- 새 콘텐츠 추가에 core 수정 불필요
- 저장/복원/실패/재시도 경로 검증
- 720p/FHD/QHD 검수
- placeholder ColorRect/Label이 월드 오브젝트 역할로 남지 않음
- 상시 shell HUD 없음
- 필요한 전환에서 Input Bubble 동작
- 사용자가 직접 플레이해 검토할 수 있는 상태
