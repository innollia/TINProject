# TIN UI 구현·검수 규칙

UI를 만들거나 수정·검수하기 전에 읽는다. [UI_WORKFLOW.md](UI_WORKFLOW.md)가 공통 계약을 소유하고, 이 문서는 그 계약을 실제 작업에서 확인할 규칙으로 구체화한다.

2026-09-26 사용자가 지정한 [UI Skills](https://www.ui-skills.com/)에서 네 자료를 선별했다. 외부 skill을 설치하거나 통째로 실행하는 문서가 아니다. 아래 채택 원칙에 TIN의 상태·입력·해상도 계약을 결합했으며, Godot 적용과 판정 과제는 프로젝트용으로 작성했다.

## 적용 범위와 우선순위

- 최신 사용자 결정과 프로젝트 계약을 지킨다. 구체 화면 문법은 해당 `plans/kits/` 계획의 Primary Reference 하나를 따른다. 이 문서는 새 Primary/Secondary Reference가 아니다.
- 색·글꼴·밀도·패널 형태를 웹사이트 취향으로 교체하지 않는다. 아트는 [VISUAL_DIRECTION.md](VISUAL_DIRECTION.md), 제작은 [IMAGE_ASSET_WORKFLOW.md](IMAGE_ASSET_WORKFLOW.md)를 따른다.
- 아래 규칙은 작업 대상 화면에 적용한다. 관련 없는 화면 전수 개편, 신규 HUD, 전역 UI 서비스, 새 패키지 도입의 근거가 되지 않는다.
- 기존 계획의 화면 구조나 입력 계약을 바꿔야 하면 계획부터 갱신한다. 외부 지침과 충돌할 때 기존 결정을 재질문하지 말고 충돌한 항목만 기록한다.

## R1. 화면의 기준과 실제 연결부터 확인한다

수정 전 아래 연결을 짧게 기록한다.

`Primary Reference의 실제 상태/캡처 → 따라갈 UI 패턴 → TIN 화면/상태 → 적용할 차이 → 검수 과제`

- 기존 구현을 고칠 때는 그 화면을 여는 경로와 실제로 쓰는 scene/script/Theme를 확인한다. 파일명이 비슷하거나 검색에 걸렸다는 이유로 사용 중이라고 판단하지 않는다.
- 문제는 적용 계약, 발생 위치, 재현 입력, 플레이어에게 생기는 결과를 갖춰 기록한다. 취향 차이를 버그로 단정하지 않는다.
- 가독성·정보 계층·밀도는 실행 화면으로 판단한다. 코드만 읽었다면 해당 시각 항목은 미검수다.
- Retired Prototype의 UI·아이디어를 개선 예시로 끌어오지 않는다. [PROJECT_DECISIONS.md](../PROJECT_DECISIONS.md)의 현재 적용 결정을 확인한다.

**판정 과제:** 이 변경이 필요한 이유를 실제 화면 상태와 해당 계약 하나로 설명할 수 있어야 한다.

## R2. Focus·선택·실행 결과를 구분한다

- `focus`는 다음 입력 대상, `selected/active`는 현재 선택·적용된 값이다. 선택 후 focus를 옮겨도 어느 값이 적용됐는지 읽혀야 한다.
- hover에서만 보이는 필수 정보는 해당 화면의 키보드/패드 focus로도 접근할 수 있어야 한다. 색 변화만으로 focus를 표현하지 않는다.
- Control 기반 메뉴는 초기 focus, 이동 순서, 닫기 후 복귀 대상을 정의한다. 목록에서 대상이 사라지거나 비활성화되면 유효한 다음 대상 또는 빈 상태의 닫기 대상으로 이동한다.
- 모달 화면이 열렸을 때 입력이 뒤의 메뉴나 월드까지 중복 전달되지 않아야 한다. 스크롤·패널·연출이 focus 대상을 가리지 않게 한다.
- 입력은 기존 InputMap action과 ModuleContext 계약을 사용한다. 키 안내는 Input Bubble 계약을 지키며 상시 설명문으로 보충하지 않는다.

**판정 과제:** 마우스 없이 열기 → 이동 → 선택 → 취소 → 다시 열기를 수행한다. 선택값과 focus 복귀가 유지되고, 지원 입력 장치를 바꿔도 필수 정보에 접근할 수 있어야 한다.

## R3. 내용이 바뀌어도 조작 위치가 흔들리지 않게 한다

- Control의 바깥 경계는 anchor, 내부 정렬은 Container를 우선한다. Container가 관리하는 자식의 위치를 수동 좌표로 다시 제어하지 않는다.
- 초상·미리보기 등 UI 이미지 영역은 실제 로드·교체 전후 같은 배치 기준을 유지한다. 이미지 원본 크기 차이로 주변 버튼이 밀려서는 안 된다.
- 선택 전후의 글꼴·테두리·상세 내용 변화가 주변 항목과 클릭 영역을 밀어내지 않게 한다. 필요한 공간을 확보하거나 별도 상세 영역을 사용한다.
- 긴 한국어·최대 숫자·빈 목록의 처리 방식을 정한다. 비교에 필요한 숫자와 단서는 말줄임으로 숨기지 않는다. 줄바꿈·스크롤·상세 보기 중 화면 문법에 맞는 방식을 계획에 명시한다.
- 작은 해상도 문제를 해결하려고 필수 정보를 삭제하거나 월드 플레이 영역을 덮지 않는다. 월드 격자 계산은 UI 반응형과 분리하고 셀 비율을 보존한다.

**판정 과제:** 1280×720 / 1920×1080 / 2560×1440에서 짧은 내용·긴 내용·빈 상태·최대 데이터를 번갈아 표시한다. 겹침, 잘림, focus 이탈, 의도하지 않은 조작 위치 이동이 없어야 한다.

## R4. 모션은 현재 입력과 상태를 따라간다

- 연출마다 전달할 사건을 하나 적는다. focus 이동, 선택 확정, 화면 복귀, 세계 변화 중 무엇을 설명하는지 불분명하면 추가하지 않는다.
- 반복 탐색에 항목별 순차 등장이나 긴 대기를 붙이지 않는다. 시간·배율·곡선은 Primary Reference와 반복 조작으로 정하며 웹 예제의 수치를 복사하지 않는다.
- 열기 도중 닫기, 빠른 대상 변경처럼 새 입력이 들어오면 이전 표현 전환을 취소하거나 현재 상태로 재지정한다. 오래된 완료 콜백이 닫힌 화면을 다시 열거나 이전 선택을 덮어쓰면 실패다.
- Tween/AnimationPlayer의 대상 속성과 소유 화면을 정한다. 닫기·모듈 교체 후 이전 화면의 연출이나 콜백이 새 화면에 영향을 주지 않게 한다.
- 표현 연출의 완료 여부를 domain 성공 판정으로 삼지 않는다. 장르 규칙상 입력 잠금이 필요한 경우에는 계획에 근거와 해제 조건을 적는다.
- 모션이 끝나거나 생략되어도 결과 상태가 형태·선·위치·텍스트 등으로 남아야 한다. Reduced Motion을 구현하는 Kit에서는 입력·성공 판정을 유지하는 대체 표현을 검수한다.

**판정 과제:** 빠르게 열기/닫기와 연속 선택을 반복한다. 입력 손실·이중 실행·이전 상태 재등장이 없어야 하며 정지 화면에서도 최종 선택과 결과를 읽을 수 있어야 한다.

## R5. 실패·대기·복귀를 실제 상태로 표현한다

- disabled, 처리 중, 실패, 성공을 구별한다. 사용할 수 없는 항목은 실행 intent를 내보내지 않아야 한다.
- 대기는 실제로 시간이 걸리는 작업에만 표시한다. 짧은 로컬 작업에 가짜 로딩 시간이나 토스트를 추가하지 않는다. 진행률은 측정 가능한 값이 있을 때만 표시한다.
- 저장/불러오기처럼 시스템 작업이 실패하면 해당 문맥에서 원인과 가능한 다음 행동을 짧게 보여준다. 추리 정답이나 게임 규칙을 설명문으로 노출하라는 뜻은 아니다.
- 이미 실패한 작업을 성공한 것처럼 표시하지 않는다. 재시도·취소 후의 화면과 focus는 현재 domain 상태에서 다시 구성한다.
- 장르의 빠른 undo/reset과 저장 데이터 삭제를 같은 확인 절차로 묶지 않는다. 복구·확인 정책은 기존 Kit/Shell 계약을 따른다.

**판정 과제:** 해당 화면에 존재하는 불가 행동·작업 실패·취소·재시도를 수행한다. 결과 표시와 실제 상태가 일치하고 다시 조작 가능한 곳으로 돌아와야 한다.

## R6. 검수는 작업 범위와 증거를 남긴다

- 구현 변경은 [AGENTS.md](../AGENTS.md)의 자동 검증 순서를 따른다. 상태와 intent, focus 복귀, 중복 입력은 자동 검증하고 시각적 판단은 실제 실행으로 확인한다.
- 해당 화면에 적용되는 R1~R5 판정 과제를 수행한다. 존재하지 않는 로딩·모달·Reduced Motion 기능을 체크리스트를 채우려고 새로 만들지 않는다.
- 정지 캡처는 배치·focus 증거다. 모션과 입력 감각은 실제 조작 기록 또는 영상으로 구분한다.
- 실패 기록은 `규칙 ID | 화면/상태 | 재현 입력 | 기대/실제 | 코드 위치 또는 캡처 | 수정/재검수 결과`로 남긴다. 같은 원인은 묶고, 확인하지 못한 항목은 이유와 함께 미검수로 표시한다.
- 문서만 바꾼 경우 링크·용어·계획 경로·Retired Prototype 경계를 확인한다. 게임 실행이나 시각 검수를 했다고 쓰지 않는다.
- UI 검수 통과는 Kit 전체 완료를 대신하지 않는다. 사용자 직접 플레이 전에는 **검토 준비 완료**까지만 선언한다.
