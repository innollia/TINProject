# TINProject — Design Philosophy

이 문서는 TINProject의 **설계 철학 단일 출처**다.

- `PROJECT_DECISIONS.md`: 사용자 확정 결정
- `AGENTS.md`: 작업 절차·아키텍처·검증 규칙
- `plans/`: 아직 구현하지 않은 구체 작업
- 이 문서: 그 결정과 작업을 해석할 때 사용하는 **설계 사고방식**

계획서에 아래 원칙을 반복해서 적지 않는다. 계획서는 이 문서를 링크하고 해당 모듈 고유 내용만 기록한다.

---

## 1. 프로젝트 전체와 게임형 모듈을 구분한다

TINProject 전체에는 공통 코어 루프가 없다.  
게임과 게임 사이에서 장르, 조작, 저장 방식, 화면 문법이 크게 바뀔 수 있다.

하지만 **한 게임형 모듈 내부는 하나의 게임**이어야 한다.

게임형 모듈 하나를:

```text
짧은 퍼즐 A
→ 별도 조작의 미니게임 B
→ VN C
→ 또 다른 미니게임 D
```

처럼 묶어 분량을 만들지 않는다.

한 게임형 모듈에서는 플레이어가 익숙해지고 재사용할 수 있는 지속적인 플레이 문법이 있어야 한다.  
지역·사건·NPC·도구·규칙·지식이 늘어날수록 **같은 게임에서 가능한 상황이 넓어지는 것**이 기본이다.

일회성 변칙 기믹은 허용한다.  
하지만 콘텐츠 대부분이 매번 새 규칙 설명이나 새 입력 체계를 요구하면 다시 미니게임 릴레이다.

---

## 2. 모듈은 여러 크기로 존재한다

`module`은 하나의 크기만 뜻하지 않는다.

### 소규모 모듈

- 짧은 상황
- 장면
- 기믹
- 공간
- 전환
- 한 번 쓰는 특수 연출

현재 구현된 소규모 모듈은 유효한 자산이다.  
짧다고 실패한 게임이 아니며, 동결·삭제·강등할 이유가 없다.

### 게임형 모듈

Mosa Lina, Golden Idol, 2D Librarian, Library of Babel 게임화, 전파계 비주얼노벨, Artis Impact, ODDADA, Motorslice, In Stars and Time, Baba Is You, Taiji, West of Loathing, Plug & Play, Stone Story RPG 같은 사용자 제시 후보가 여기에 해당한다.

게임형 모듈은 그 안에 **약 30분~8시간 규모의 authored content를 품을 수 있는 두께**를 지향한다.

이 수치는:
- 강제 체류시간이 아님
- 클리어 시간도 아님
- 플레이어가 실제로 전부 볼 필요도 없음

플레이어는 3분이나 20분만 머물고 다른 게임으로 넘어갈 수 있다.

---

## 3. 아이디어 풀은 명세가 아니다

사용자가 한 번에 많은 아이디어를 던질 수 있다.  
그것들은 기본적으로 **재료 풀**이다.

- 전부 사용할 필요 없음
- 최근에 나온 아이디어가 자동 우선순위가 아님
- 길게 적힌 아이디어가 자동 중심 설정이 아님
- 서로 붙어 적혔다고 같은 세계/캐릭터/게임으로 합치지 않음
- 하나의 아이디어를 억지로 게임형 모듈로 승격하지 않음
- 선택되지 않은 아이디어는 폐기된 것이 아님

게임형 모듈을 설계할 때는 최근 덤프 몇 개가 아니라:
- 프로젝트 전체 방향
- 기존 사용자 아이디어
- 기존 게임형 후보
- 현재 필요한 콘텐츠 두께
를 함께 본다.

선택한 게임에 자연스럽게 맞는 아이디어만 흡수한다.

---

## 4. 아이디어를 흡수하는 방법

아이디어 하나마다 전용 gameplay mode를 만들지 않는다.

가능하면 현재 게임의 기존 문법 안에서:

- 세계관
- NPC
- 지역
- 사건
- 아이템
- 대사
- 규칙 변형
- 숨은 공간
- 반복 등장 요소

등으로 흡수한다.

예를 들어 "이상한 종교" 아이디어가 있다고 해서 종교 미니게임을 새로 만들 필요는 없다.  
현재 게임이 RPG/어드벤처라면 그 게임의 마을·NPC·아이템·반복 사건으로 존재할 수 있다.

아이디어를 넣기 전에 묻는다.

1. 이 게임의 기존 문법으로 자연스럽게 플레이되는가?
2. 세계와 콘텐츠 밀도를 늘리는가?
3. 새 규칙 설명과 전용 런타임을 요구하는가?
4. 이 조각을 빼도 게임 자체는 서는가?

---

## 5. 한 게임으로 오래 굴러갈 중심을 먼저 찾는다

잘못된 방식 A:

```text
최근 아이디어 여러 개
→ 각각 플레이 가능한 장면으로 만듦
→ 한 폴더에 묶음
```

이것은 미니게임 앤솔로지가 되기 쉽다.

잘못된 방식 B:

```text
유명 게임 하나 선택
→ 그 코어 루프 복제
→ 사용자 아이디어를 거기에 끼워 넣음
```

이것은 사용자 아이디어의 맛을 평범하게 만들기 쉽다.

대신:

```text
넓은 아이디어 풀과 프로젝트 방향 확인
→ 한 게임으로 30분~8시간 굴러갈 중심 후보 선택
→ 같은 게임 문법으로 충분한 authored content가 나오는지 검증
→ 잘 맞는 아이디어 조각만 흡수
→ 반복적으로 필요한 시스템 구체화
```

게임형 모듈 후보는 다음을 만족할수록 좋다.

- 30분 뒤에도 같은 기본 게임을 하고 있음
- 이전에 배운 규칙·도구·지식을 다시 사용함
- 새 콘텐츠가 새 미니게임보다 새 상황을 만듦
- 3분만 봐도 재미있지만 더 머물면 훨씬 많은 콘텐츠가 있음
- 특정 아이디어 하나를 빼도 게임 중심이 유지됨
- 다른 authored content를 계속 받아들일 수 있음

---

## 6. 콘텐츠 두께는 반복으로 만들지 않는다

30분~8시간의 분량은 다음으로 부풀리지 않는다.

- 절차적 생성만 반복
- 적 HP 증가
- 같은 퍼즐 재색칠
- 같은 대화 구조 반복
- 이동 거리
- 수집 개수
- 의미 없는 숫자 성장

분량은 **새로운 authored 상황·발견·관계·공간·규칙 적용·재해석**으로 늘린다.

게임형 모듈의 초기 구현에서 시스템 기반을 먼저 튼튼하게 만드는 이유도,
샘플 두 개로 끝내기 위해서가 아니라 이후 authored content를 빠르고 안전하게 많이 추가하기 위해서다.

---

## 7. 시스템 우선의 정확한 의미

설계 단계:

```text
게임 중심
→ 필요한 콘텐츠의 폭
→ 반복해서 필요한 능력
→ 시스템
```

구현 단계:

```text
시스템 기반
→ 검증용 최소 콘텐츠
→ authored content 증설
```

"시스템 우선"은 다음을 뜻하지 않는다.

- 콘텐츠보다 추상화를 사랑하라는 뜻 아님
- 모든 장면을 하나의 범용 엔진으로 표현하라는 뜻 아님
- 여러 미니게임을 쉽게 꽂는 ScenarioHost를 만들라는 뜻 아님
- 미래의 재사용을 상상해 shared를 미리 만들라는 뜻 아님

두 번째 실제 재사용 사례가 생기기 전에는 shared 추상화를 만들지 않는다.

---

## 8. Adopt → Adapt → Build

어려운 subsystem은 처음부터 직접 만들지 않는다.

순서:

1. 현재 TIN 내부 구현 확인
2. 공개 저장소 / Godot Asset Library / 공식 addon 조사
3. permissive license와 구조가 맞으면 채택
4. 전체 구조가 안 맞으면 필요한 subsystem만 추출
5. 오래된 버전이면 필요한 알고리즘/구조만 포팅
6. 라이선스·품질·구조가 막으면 직접 구현

외부 코드 때문에 TIN 전체 아키텍처를 바꾸지 않는다.

특히:
- autoload
- 전역 EventBus
- 전역 save
- Input singleton
- 외부 프로젝트의 전체 routing

을 그대로 들여오지 않는다.

외부 베이스는 TIN 모듈 계약 안에 가둔다.

---

## 9. 이상함을 설명해서 평범하게 만들지 않는다

TINProject의 이상한 설정은 끝까지 이상한 채로 존재할 수 있다.

- 관계가 설명되지 않아도 됨
- 세계 간 연결 원리가 통일되지 않아도 됨
- 메타 현상을 캐릭터가 친절하게 해설하지 않음
- 기묘한 농담에 반드시 비밀 진실/반전을 붙이지 않음
- 설정을 합리화하기 위해 장황한 lore를 만들지 않음

플레이어가 직접 겪는 발견과 변화가 설명문보다 우선한다.

---

## 10. 사용자 확정과 AI 제안을 섞지 않는다

항상 구분한다.

- **USER-CONFIRMED**: 사용자가 직접 확정
- **AI-INFERRED DEFAULT**: 구현을 위해 임시 제안
- **CURRENT IMPLEMENTATION FACT**: 현재 코드가 실제로 하는 것
- **TBD**: 아직 결정되지 않음

AI가 임의로 만든:
- 이름
- 국가
- 라우트
- 숫자
- 사건 원인
- 세계관 연결
을 사용자 canon으로 승격하지 않는다.

사용자의 `몰라/모름`은 이전 확정사항을 자동 취소하지 않는다.

---

## 11. 기존 사용자 설계를 오래됐다는 이유로 버리지 않는다

"옛 설계"라는 이유로 기존 사용자 작성 내용을 폐기하지 않는다.

문제가 생겼을 때 먼저 구분한다.

- 설계가 문제인가?
- 구현 해석이 문제인가?
- 콘텐츠 양이 문제인가?
- 시스템 깊이가 문제인가?

특히 기존 소규모 모듈이 얕아 보인다고 해서:
- 동결
- 삭제
- 강등
- 흡수 강제
하지 않는다.

그들은 여전히 사용할 수 있는 작은 콘텐츠 단위다.

---

## 12. 지식 기반 플레이는 별도 기준을 따른다

지식 기반 요소를 표방할 때는 `docs/KNOWLEDGE_BASED_DESIGN.md`를 따른다.

모든 게임형 모듈을 지식 게임으로 만들 필요는 없다.

지식 기반의 핵심은 단순 정답 입력이 아니라:
- 규칙
- 구조
- 언어
- 인과
- 사실
- affordance
를 이해한 뒤 플레이 방식이 달라지는 것이다.

---

## 13. TINProject 전체의 변화와 한 게임 내부의 변화

TINProject 전체:
- 게임 사이 장르 변화 자유
- 저장 규칙도 달라질 수 있음
- 연결 방식도 달라질 수 있음
- 공통 성장 루프 없음

한 게임형 모듈 내부:
- 하나의 게임으로 느껴져야 함
- 기존 문법을 재사용
- 콘텐츠가 서로 상태/지식/공간/캐릭터를 통해 이어짐
- 일회성 변칙은 가능하지만 기본 문법을 대체하지 않음

이 둘을 혼동하지 않는다.

---

## 14. 설계 문서 작성 규칙

계획서에는 이 철학을 다시 설명하지 않는다.

계획서에 남길 것:

- 목적
- 사용자 확정 콘텐츠
- 해당 게임 고유 플레이 문법
- 데이터/상태
- 파일
- 외부 베이스
- 구현 단계
- 테스트
- 완료 기준
- 미정/비목표

계획서에 반복하지 않을 것:

- 모듈 규모 철학
- 아이디어 풀 해석법
- 미니게임 릴레이 금지 원칙
- 시스템 우선의 일반론
- Adopt → Adapt → Build 일반론
- 사용자/AI 구분 일반론

필요하면 첫머리에:

> 공통 설계 원칙: `docs/DESIGN_PHILOSOPHY.md`

한 줄만 둔다.

## 15. 기능 완료와 화면 완료를 분리한다

테스트 통과, 저장 복원, 입력 처리, 상태 전이가 맞는 것은 기능 완료다. 그것만으로 플레이 가능한 화면이 완성된 것은 아니다.

플레이어가 실제로 보는 화면은 별도의 산출물로 취급한다.

- 구현 전에 상용 게임의 실제 화면을 확인한다.
- 레퍼런스는 "분위기 비슷하게"가 아니라 구도, 시선 흐름, 정보 계층, 오브젝트 밀도, 상호작용 피드백 단위로 해체한다.
- 각 주요 화면은 무엇이 초점인지, 무엇이 월드인지, 무엇이 UI인지, 입력 전/후 상태가 어떻게 달라지는지를 계획서에 적는다.
- 개발용 ColorRect, 임시 Label, 텍스트로 적은 사물명, 디버그 패널은 최종 표현으로 승격하지 않는다.
- 텍스트 자체가 세계의 오브젝트이거나 게임 규칙인 경우는 예외다.

상용 게임 레퍼런스는 복제 대상이 아니라 품질 하한과 화면 문법을 고정하는 기준이다. 원작의 고유 자산·문구·레벨·캐릭터 디자인은 가져오지 않는다.

## 16. at-icons는 아이콘 세트가 아니라 콜라주 재료다

res://addons/at-icons/의 아이콘 에셋은 월드 아트의 형태 원재료다.

허용:
- 서로 다른 아이콘의 일부를 캐릭터의 머리·몸·사지·장식으로 재조립
- 원래 의미와 무관한 조각을 지붕·창문·기계·식물·가구 실루엣으로 재배치
- 회전, 비균일 스케일, 자르기, 가리기, 미러, 겹치기, 색 변형
- 2D에서는 TextureRect/Sprite2D 조합, 3D에서는 Sprite3D/평면 콜라주 등으로 세계 오브젝트화

금지:
- 아이콘 하나를 원래 의미 그대로 표지판이나 오브젝트의 기호로 사용
- 집 아이콘=집, 사람 아이콘=사람처럼 그대로 대응
- 메뉴, HUD, 버튼, 탭, 상태 배지, 저장/설정/뒤로가기 같은 UI 아이콘
- 원본 아이콘 한 장을 확대해 완성 아트로 취급

주요 캐릭터·건물·화면 초점 오브젝트는 기본적으로 2종 이상의 원본 조각을 합성하거나, 단일 원본을 썼다면 원래 픽토그램으로 읽히지 않을 정도로 변형한다.
