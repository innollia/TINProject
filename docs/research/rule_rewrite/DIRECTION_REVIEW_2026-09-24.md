# Rule Rewrite Kit 구현 중 방향 점검 — 2026-09-24

상태: 2026-09-24 사용자 요청으로 일시정지 후 3분 방향 고찰을 거쳐 구현 재개. 이 문서는 당시 구현과 계획의 차이를 기록한다. Kit 완료 판정이나 새 사용자 결정이 아니다.

## 1. 조사 자료가 실제로 준 도움과 한계

- [레퍼런스 보고서](../RULE_REWRITE_REFERENCE_REPORT.md)의 원작 플레이 자료와 커뮤니티 규칙 목록은 지원할 단어, 턴 순서의 시험 항목, 실패·3D 화면 비교 대상을 정하는 데 도움이 됐다. [모드 생태계 보고서](../RULE_REWRITE_MOD_ECOSYSTEM_REPORT.md)의 PlasmaFlare 가이드는 재파싱과 rule table 같은 구조를 찾는 길잡이다.
- 이를 **원작 코드 로직을 검증했다**고 부르면 안 된다. 가이드는 비공식·불완전한 모딩 문서이고, 보고서는 위키·README·영상·공식 업데이트의 출처 수준을 구분한다. 현재 TIN의 METRIX/INV/OWNS와 다수의 충돌 순서는 TIN 계약과 구현·테스트로 정한 것이며 원작 내부 코드와 일치한다고 증명하지 못했다.
- 조사→계획→지원 어휘 대량 구현으로 곧바로 넘어간 것이 문제였다. 실제 퍼즐 보드가 핵심 조작을 강제하는지 확인하기 전에 시스템 테스트가 녹색이 됐다. 앞으로 원작 자료는 작은 대조 보드의 예상 동작을 세우는 데 쓰고, 실제 플레이와 비교해 적용한다. 확인되지 않은 원작 세부는 TIN 결정이라고 표시한다.

## 2. 속도

- 느린 플레이는 목표 동작이 아니다. 재개 뒤 동일한 headless 계측 하네스에서 3회 warmup·12회 샘플로 얻은 **수정 전 기준값**은 아래와 같다. 실제 창의 입력 체감은 별도 확인이 필요하다.

  | 보드·화면 | 도메인 턴 중앙값 | 화면 재구성 중앙값 | 명령→다음 process frame 중앙값 |
  |---|---:|---:|---:|
  | 01, 2D | 16.0 ms | 299.4 ms | 286.8 ms |
  | 14, 3D·89 entities | 313.7 ms | 878.7 ms | 1536.4 ms |

- 확인된 주 병목은 [rule_board_view.gd](../../../modules/rule_rewriting/presentation/rule_board_view.gd)의 `show_state()`가 2D 입력에서도 `_sync_world()`를 호출하고, `_sync_world()`가 3D 노드를 지운 뒤 바닥 타일·모든 물체·cutout을 다시 만드는 것이다. 3D의 도메인 턴도 느리므로 [module.gd](../../../modules/rule_rewriting/module.gd)의 반복 `_rebuild_derived()`와 WORD 고정점 재파싱을 별도로 프로파일링해야 한다.
- 실제 GL Compatibility **창**에서도 같은 하네스로 3회 warmup·12회 샘플을 측정했다. 01 2D는 명령→draw 중앙값 555.4 ms, 도메인 intent 35.8 ms, 동기 view rebuild 525.4 ms. 14 3D는 명령→draw 2655.8 ms, 도메인 508.6 ms(그중 METRIX resolver 147.3 ms), 동기 view rebuild 1498.7 ms. 하네스는 `tests/performance/rule_rewrite_benchmark.gd`; 이 수치들은 수정 전 기준값이며 구현 변경 뒤 재측정해야 한다.
- 수정 후 동일한 보드·입력·계측 방식으로 비교하고, 실제 창에서도 입력 반응을 확인한다. 의미 검증 없이 파서 결과를 캐시하거나 규칙 지원 범위를 줄여 속도를 얻지 않는다. 속도 문제가 해결되기 전에는 콘텐츠 수 증가를 진척으로 세지 않는다.

## 3. 규칙 변경 안내문

- 현재 [module.gd](../../../modules/rule_rewriting/module.gd)는 규칙 signature가 달라질 때마다 `밀린 단어의 문장이 바뀌었다.`를 `_message`에 넣고, [rule_board_view.gd](../../../modules/rule_rewriting/presentation/rule_board_view.gd)는 그 문장을 상단 패널로 띄운다.
- 이는 [계획서 §8](../../../plans/kits/01_RULE_REWRITE_KIT.md)의 “해당 단어와 영향 물체에 짧은 변화 표시”와 다르다. [계획서 §1](../../../plans/kits/01_RULE_REWRITE_KIT.md)은 규칙을 보드 안에서 읽게 하며, [UI 계약](../../KIT_WORKFLOW.md)은 설명문이 조작을 대신하는 것을 금지한다. 조작 대상 전부 상실 시의 Undo/Restart 안내는 별도로 계획된 회복 UI다.
- 재개 시 반복 문구를 제거하고, 실제 변한 단어·물체의 현장 반응을 구현·검수한다. 상태 원인은 보드에서 읽혀야 한다. 실패·성공처럼 별도 근거가 있는 안내는 각각 검증한다.

## 4. at-icons 아트 적용 — 과거 구현 상태

이 절은 2026-09-24 시점 구현의 역사적 평가다. 2026-09-25 사용자 지시에 따라 at-icons 제작 문서·규칙·실험은 별도 아카이브로 옮기며, 아래 수정 권고는 현행 이미지 제작 지침이 아니다.

- 현재 [ICON_RECIPES](../../../modules/rule_rewriting/presentation/rule_board_view.gd)는 오브젝트 종류별로 아이콘 이름 두 개를 고정한다. 2D에서는 회전·크기·색을 조금 달리해 겹치고, 3D에서는 대부분 기본 BoxMesh 또는 SphereMesh 위에 두 Sprite3D를 얹는다. 캡처에서는 일부 몸체의 형태가 비슷하고 아이콘 조각의 의미가 그대로 읽힌다.
- 이는 [아트 계약](../../VISUAL_DIRECTION.md)의 crop·rotation·mirror·비균일 scale·overlap·색 변형을 써서 여러 조각으로 독자적인 오브젝트 실루엣을 만드는 수준에 못 미친다. 현재 코드는 **아이콘을 사용했다**는 증거이지 **원하는 형태를 자유롭게 만들었다**는 증거가 아니다.
- 구현 재개 시 주요 물체별로 레퍼런스 상태와 TIN 스케치를 먼저 나란히 놓고, 원 pictogram이 읽히지 않는 복합 실루엣을 만든다. 2D·3D·inventory 썸네일이 같은 물체로 읽히는지 실제 캡처로 검수한다. 단순한 색 변경·아이콘 두 개 겹치기를 완료 기준으로 삼지 않는다.

## 5. 작업 방식에서 확인한 실패

1. **정적 테스트를 퍼즐 검증으로 과대평가했다.** 초기 14보드 검사는 ID·좌표·문장·테두리 불변식만 보았다. 실제 명령 검증에서 6·8·10·11번의 우회와 9번의 선행 완성 등 계획 과제와 다른 플레이가 나왔다. 각 보드는 승리 경로뿐 아니라 핵심 조작 발생과 쉬운 우회 실패를 검증한다.
2. **`solved=true`를 의도한 해법의 증거로 오인했다.** 8번은 FLOAT로 문을 통과해 승리했지만 KEY·GATE가 남아 있었다. 회귀 테스트는 승리뿐 아니라 원인인 entity·규칙 상태의 변화를 확인한다.
3. **기능을 한꺼번에 넓혀 결함 위치를 숨겼다.** HAS 생성, WORD 고정점, METRIX 소유·조건, 3D UI를 동시에 붙인 뒤 콘텐츠에서 미연결과 저장 복원 결함을 찾았다. 재개 후에는 작은 대조 보드와 실제 명령 경로를 기능별로 먼저 완성한다.
4. **편집 중인 파일을 다른 담당이 실행했다.** 일시적 parse error가 반복됐다. 파일 소유자와 실행 검증 담당은 안정화 신호를 교환하고, 변경 중에는 전체 게이트·보드 probe를 시작하지 않는다.
5. **해상도와 화면 검증을 숫자만으로 판단했다.** 1280 창 안의 실제 렌더가 1152였고, 긴 메시지는 읽혀도 보드를 가렸다. 창·내부 viewport·셀 비율·가림을 실제 캡처와 로그로 함께 확인한다.
6. **샘플 보드 수가 플레이 시간을 대신했다.** 계획은 14보드와 실측 10분 이상이다. 아직 01→14 연속 플레이와 시간 측정이 없고 몇몇 보드는 7~25입력으로 풀린다. 보드 추가 여부는 전체 플레이 후 정한다.
7. **임시 probe가 작업 트리에 남았다.** 현재 `tests/core/`와 저장소 루트에 임시 스크립트·로그가 untracked로 보인다. 재개 시 담당자가 소유한 probe의 필요성을 분류하고, 정식 회귀 테스트만 남긴다. 사용자 또는 다른 작업자의 파일은 추측으로 삭제하지 않는다.

## 6. Grilling frontier

현 시점에서 새 project-wide 결정을 묻지 않는다. 1~5번 문제는 이미 정해진 계획과 구현의 차이이거나 먼저 측정할 기술 사실이다. “설명문을 유지할지”, “아이콘 두 개만 겹쳐도 될지”를 추천 승인 질문으로 만들지 않는다.

Kit별로 다시 열 가능성이 있는 질문은 **실제 플레이와 비교해도 계획이 양립할 수 없을 때**만 제시한다. 예를 들어 2D에서 INV UI를 숨기면서 11번의 ‘넣고 빼기’를 물리 보드만으로 이해시키기 어려운지, 3D 핫바의 Minecraft 확장과 Baba의 보드 가독성이 동시에 성립하는지를 사용자 플레이에서 확인한다. 그 전에는 계획된 문법을 먼저 구현·검수한다.

## 7. 보드 수와 완료 판정

- 현재 계획: **연속 플레이 14개 authored 보드**. loader index의 옛 2개는 직접 로드 호환용이며 정규 진행에 들어가지 않는다.
- [계획서 §12](../../../plans/kits/01_RULE_REWRITE_KIT.md)는 core 수정 없이 **15번째 보드**를 추가해 확장성을 증명하도록 요구한다. 이것은 지금부터 스테이지를 무한히 늘린다는 뜻이 아니다.
- 14라는 수는 10분을 보증하지 않는다. 01→14 실제 연속 플레이를 재고, 10분 미만이면 기다림·긴 이동·반복 입력 대신 서로 다른 규칙 조합의 유의미한 콘텐츠를 보강하거나 추가한다. TIN 본편 전체의 스테이지 수 목표는 정해진 바 없다.
