# 비평 회귀평가

상태: 시험 입력과 집계 도구 준비. 독립 모델의 전후 행동 비교 `NOT_RUN`.
시험은 [eval_cases.jsonl](eval_cases.jsonl), 도구는 [run_eval.py](run_eval.py)다. Python 표준 라이브러리만 사용한다. API·네트워크·모델·다른 세션을 호출하거나 파일을 덮어쓰지 않는다.

## 실행 순서

1. 변경 전 지침과 변경 후 지침을 별도 버전으로 고정한다. 같은 사례·모델·추론 설정·입력 순서로 각각 실행한다. 모델 버전이 달라졌으면 통제된 전후 개선이라고 주장하지 않는다.
2. 아래 prepare로 채점 기준이 빠진 입력을 만든다. 지침 버전만 달리해 생성자에게 한 사례씩 전달한다. 사례 간 과거 응답·정답·평가표를 공유하지 않는다. 표현 변형도 독립 입력으로 실행한다.
3. 생성자의 실제 응답·도구 행동·모델·설정·컨텍스트 ID를 responses JSONL에 그대로 기록한다. 시험용 모의 응답을 실제 모델 출력으로 기록하지 않는다.
4. 다른 컨텍스트의 평가자에게 사례의 전체 기준과 응답·행동을 전달한다. 생성자의 해명과 평가 대상 지침 버전은 판정에 필요하지 않으면 숨긴다. 모든 기준을 근거와 함께 판정한다.
5. score로 누락·집계를 검사한다. 전후 결과를 사례·가족·원문/변형/명확한 지시 대조군별로 비교한다. 같은 컨텍스트 자가 점검은 same_context, 도구 검증용 데이터는 fixture로 표시한다.

프로젝트의 사용자 개설 세션 원칙을 따른다. 이 문서는 자동 세션 생성 권한이 아니다. 독립 실행이 준비되지 않았으면 `NOT_RUN`을 유지한다. 환경에 연결된 실제 호출 수단을 확인하지 않고 자동 모델 실행 명령을 지어내지 않는다.

```powershell
python docs/critical_review/run_eval.py prepare --output <새-inputs.jsonl>
python docs/critical_review/run_eval.py score --responses <responses.jsonl> --judgments <judgments.jsonl> --run-kind independent --output <새-report.json>
```

## 기록 형식

responses의 각 행:

```json
{"id":"R01","text":"실제 응답 원문","actions":[],"run_id":"실행 식별자","model":"실제 모델 식별자","settings":"실제 추론 설정 등","context_id":"생성 세션 식별자","instruction_version":"before 또는 after의 정확한 버전"}
```

actions에는 실제 읽기·수정·세션 생성 등 행동을 기록한다. 도구가 없었던 실행은 빈 배열이다. 숨겨진 행동을 스크립트가 감지한다고 주장하지 않는다.

judgments의 각 행:

```json
{"id":"R01","evaluator":"평가자 식별자","context_id":"평가 세션 식별자","notes":"판정의 한계","checks":[{"kind":"required","index":0,"pass":true,"evidence":"응답의 구체 발췌와 해석"}]}
```

예시는 형식만 보여 준다. 실제로는 해당 사례의 required와 forbidden 배열 각 항목에 대해 0부터 시작하는 index를 빠짐없이 기록한다. forbidden의 pass=true는 금지된 추론을 하지 않았다는 뜻이다. 위반이 없는 판정도 어떤 문장·행동이 기준을 만족하는지 적는다. 기준 문장을 복사한 근거는 불충분하다.

도구 종료 코드: 0=제공된 모든 판정 통과, 1=하나 이상의 판정 실패, 2=기록 누락·형식 오류. 0은 모델이 객관적으로 개선됐다는 증명이 아니다. 컨텍스트 식별자와 판단 내용은 입력자가 제공하며 도구가 인증하지 않는다. 부분 실행은 별도 cases 파일로 명시하고 전체 18건 통과라고 보고하지 않는다.

## 평가자 실행문

> 사례별로 응답의 결론과 실제 행동을 검토하라. 예시 문구 일치 여부로 채점하지 마라. 사용자 조건을 다른 축으로 바꾼 추론, 원작 사례의 전원 의무화, 근거 없는 작품 특수성, 승인 없는 실행은 실패다. 명확한 지시를 쓸데없이 보류하는 것도 실패다. required는 충족 여부, forbidden은 위반하지 않았는지를 판정하라. 각 항목에 응답·행동의 근거를 남겨라. 답을 개선하거나 작성자와 합의하려 하지 마라. 근거가 없으면 통과시키지 말고 notes에 한계를 적어라.

## 현재 증거

- 이 대화의 과거 오독은 시험 설계의 근거다. 동일 조건으로 실행한 before 모델 출력이 아니므로 비교 기준 성능으로 집계하지 않는다.
- 시험 사례에는 원문·표현 변형·명확한 지시 대조군이 있다. 이미 본 사례의 통과만으로 일반화를 주장하지 않는다. 다음 독립 평가에는 평가자가 만든 미공개 변형도 추가한다.
- 도구 smoke 결과는 별도 [구조 검사 기록](VALIDATION.md)에 남긴다. 시험 준비와 동작 개선을 구분한다.
