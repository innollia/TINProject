# TIN UI 작업 계약

설계 의미는 [DESIGN_PHILOSOPHY](DESIGN_PHILOSOPHY.md), 시각 표현은 [VISUAL_DIRECTION](VISUAL_DIRECTION.md), 런타임 경계는 [MODULE_CONTRACT](MODULE_CONTRACT.md), 실행 절차는 [AGENTS](../AGENTS.md)가 기준이다. 이 문서는 셸·기록·목록·기존 모듈·신규 모듈·콘텐츠 증설의 UI 계획과 검수에 적용한다.

## 출처와 적용 경계

2026-09-22 사용자가 제공한 「고도엔진 기반 바이브코딩 게임 UI 심층 연구 보고서」의 프로젝트 적용판이다. 보고서 적용과 문서 중심 작업은 사용자 요청이다. 아래 구체적인 계약 양식과 검수 운영은 **AI 적용안**이며, 구현·실측 완료 기록이 아니다. 이번 작업에서는 보고서의 외부 출처를 재조사하지 않았다. 원문의 대화 전용 인용 ID는 검증된 저장소 출처로 옮기지 않는다.

| 보고서 제안 | TIN 적용 |
|---|---|
| 정보 계층·점진적 상세 공개·상태/표현 분리 | 채택. 화면마다 필요한 정보와 노출 조건을 적는다. |
| 네 단계 컴포넌트 체계·공통 Theme | 책임 분류로 사용. 모듈 로컬부터 시작하며 기존 Theme와 실제 사용처를 먼저 조사한다. 전 장르의 스타일을 강제로 통일하지 않는다. |
| UIRouter·TooltipService·ModalService | 책임만 식별한다. 모듈 내부 탐색은 로컬 소유, 모듈 전환은 기존 requested/앱 라우팅과 Director 경계를 유지한다. 새 전역 서비스·autoload를 만들지 않는다. |
| IconLabel·InputGlyph·아이콘 상태 표시 | UI 아이콘 금지 유지. 입력 액션의 현재 바인딩을 텍스트로 안내하고, 선택·경고는 텍스트/테두리/형태로 표현한다. |
| InputMap·포커스 | 물리 키 대신 액션을 사용하되 모듈 입력은 ModuleContext 경유. 버튼·드래그 확정·취소도 입력 차단을 준수한다. |
| GdUnit4·Godot-MCP | 도입하지 않는다. 기존 GUT 9.7.1과 통합 러너 유지. 엔진/패키지 변경은 별도 승인 범위다. |
| 60–120ms 모션·900/1800 breakpoint | 예시일 뿐 확정값이 아니다. 실제 콘텐츠와 반복 조작을 보고 정한다. |
| AAA 사례 | 구체적인 화면 구조·선택·상세 공개·탐색·모션을 직접 채택할 수 있는 UI 설계 레퍼런스다. 게임 루프의 인디게임 레퍼런스와 병행한다. [적용 지도](UI_REFERENCE_ADAPTATIONS.md)의 연결을 해당 실행 계획에서 구체화한다. |

## 구현 전 계획에 남길 계약

UI 패턴 채택, shared 추출, global service 도입, 테스트 도구 선택은 별개 판단이다. 로컬 tooltip이나 3단계 상세 보기의 채택을 모듈 격리 때문에 일반론으로 축소하지 않는다. 레퍼런스에서 확인된 구조는 상당히 유사하게 가져올 수 있다. 색상 팔레트·로고·캐릭터·고유 장식 모티프는 TIN의 표현으로 바꾼다.

구현 계획은 `Reference → 구체 패턴 → TIN 화면/상태 → adaptation`이 읽혀야 한다. “명확한 계층/적절한 피드백”만으로 끝내지 않고 무엇이 어디에 나타나고, 무엇을 선택하면 어떻게 열리고, 취소하면 어디로 돌아오는지 적는다. 실제 원작에서 확인된 사실과 보고서 작성자의 제안 및 TIN 적용안을 구분한다.

계획에는 공통 원칙을 복사하지 말고 아래 항목의 해당 화면 값을 적는다. 후보 아이디어는 미정이어도 되지만 실행 계획으로 승격할 때는 빈칸을 해소한다.

| 항목 | 기록할 내용 |
|---|---|
| 화면과 판단 | 첫 장면·1차 초점·플레이어 과제, 항상/문맥/요청 시 공개할 정보, 숨겨야 할 지식 |
| 입력 데이터 | 상태 소유자, 필드·이벤트, 초기/복원 시 갱신 시점 |
| 표시 | empty/normal/focus/selected/disabled/error/success, 긴 문자열·최대 데이터 |
| 의도 | 선택·확인·취소·되돌리기 명령, 도메인 검증 주체, 차단/연타 처리 |
| 포커스 | 열 때 대상, 논리적 탐색 순서, 닫을 때 복귀, 대상 삭제/비활성 시 대체 대상 |
| 생명주기 | bind/rebind/unbind, exit, 모달 중 하위 입력, 저장 복원·reset 후 표시와 선택 |
| 구성과 소유 | 기존 scene/Theme 재사용 조사, 변경 파일·전용 테스트, 모듈 로컬 책임, 공유 시 두 실제 사용처 |
| 시각·레이아웃 | 실제 레퍼런스 URL·화면, 1152×720 baseline, anchors/Container, 문자열 확장·배율 대응 |
| 검증 | 상태→표시·입력→의도 기대값, 수동 과제, 장치/화면 매트릭스, 증거 경로와 미검수 항목 |

노드 계층은 필요할 때만 구체화한다. 기본은 전체 Control → MarginContainer → 내용에 맞는 Container이며, 월드의 보드 좌표나 의도된 연출 배치는 UI 레이아웃과 구분한다. Container가 관리하는 자식의 위치를 수동으로 경쟁 제어하지 않는다.

## 구현 계약

- 도메인은 구체 UI 자식 노드를 참조하지 않는다. UI는 상태를 표시하고 의도를 전달하며 성공 여부를 임의로 확정하지 않는다.
- 안정적인 값과 문자열을 매 프레임 재작성하지 않는다. 초기·load/reset·변경 시 갱신하고, 실시간 물리/연출은 필요한 주기와 소유자를 명시한다.
- 바인딩을 다시 할 때 이전 대상의 연결을 해제하고 중복 연결을 막는다. 준비 전 bind와 exit 후 신호 경로도 정의한다. 보고서의 간단한 bind 예제를 그대로 완성 계약으로 쓰지 않는다.
- 버튼의 disabled 표현만으로 입력을 막았다고 판단하지 않는다. 직접 호출을 포함해 input_enabled를 확인하고, 도메인도 잘못된 명령을 거부한다. 자식 process_mode는 INHERIT다.
- 셸/오버레이가 입력을 소유할 때 하위 모듈로 같은 입력을 전달하지 않는다. 취소는 최상위 화면 하나에만 적용하고 이전 유효 포커스를 복원한다. 사라진 대상이면 안전한 첫 조작 대상으로 이동한다.
- 필수 hover 정보에는 포커스/선택 경로를 제공한다. 드래그가 있는 화면에는 선택→대상 지정→확인/취소 경로를 둔다. 터치는 배포 대상으로 정한 경우 검수한다.
- 포커스·열린 툴팁·트윈을 영구 게임 상태로 저장하지 않는다. 진행 의미가 있는 선택만 모듈 저장 계약에 명시한다. load/reset 이후 UI는 권위 있는 상태에서 재구성한다.
- Theme/Resource에는 해당 화면군의 타이포그래피·간격·상태 표현을 모은다. GameButton 등 범용 래퍼를 만드는 일 자체를 산출물로 삼지 않는다.
- UI scale/text scale과 Reduced Motion은 구현해야 할 후속 기능으로 추적한다. 저장 소유자·기존 설정과의 연결은 U3 계획에서 먼저 정하고, 미구현 옵션을 지원한다고 보고하지 않는다.

## 작업 순서

1. 기존 사용자 결정·해당 계획·기존 구현/테스트와 재사용 후보를 읽는다. 관련 테스트 기준선을 남긴다.
2. 실제 레퍼런스와 1152×720 baseline을 확보하고 위 계약을 화면 단위로 확정한다.
3. 한 화면에 필요한 최소 컴포넌트부터 구현한다. 상태/입력 테스트와 실제 실행을 확인한 뒤 상위 화면에 조립한다.
4. 반복 실패가 일반 규칙의 누락일 때만 이 문서/AGENTS를 갱신한다. 특정 화면의 예외는 그 계획에 남긴다.
5. AGENTS의 import → 통합 → GUT → smoke 이후 아래 실제 UI 검수를 수행한다. 결과와 미확인 사항을 인계한다.

문서만 변경한 작업은 링크·계획 간 모순·변경 범위를 검증한다. 게임 실행이나 UI 검수를 수행한 것으로 기록하지 않는다.

## 검증 매트릭스와 완료 증거

| 축 | 필수 확인과 판정 |
|---|---|
| 자동 계약 | 초기 상태→표시, 상태 변경/복원→표시, disabled/차단 시 명령 없음, open/close 포커스, reset/re-entry, rebind 신호 중복 없음 |
| 입력 | 핵심 메뉴를 마우스·키보드·컨트롤러 각각으로 완료. 실제 장치 검수가 없으면 시뮬레이션과 구분해 미검수로 남긴다. |
| 화면 | 1152×720(16:10) 기준. 최소/최대 지원 창 크기와 대상 종횡비를 계획에 명시하고 검수. 16:9·21:9·좁은 창의 지원 여부가 미정이면 TBD로 남긴다. |
| 텍스트·데이터 | 긴 대상 문자열 또는 의사 현지화, 빈 목록/1개/정상량/최대량, 긴 이름·큰 수, 확대 시 잘림·겹침·스크롤 |
| 접근성 | 색 이외의 상태 전달, 명확한 포커스, hover 대체, 배율 확대와 Reduced Motion에서도 같은 기능 피드백 |
| 명암 | AI 검수 기본 목표: 표준 핵심 텍스트/시각 요소 4.5:1, 큰 요소 3:1. 실제 크기·배경·상태별 측정값을 남긴다. 고대비 모드 7:1은 해당 옵션 채택 시 검수 목표이며 인증을 뜻하지 않는다. |
| 접근성 플랫폼 | 스크린리더는 지원 범위·설치 엔진 기능·실제 읽기 순서를 조사한 뒤 계획한다. API 존재만으로 지원 완료 판정 금지. |
| 모션 | 반복 선택을 지연시키거나 포커스를 가리지 않는지, 감소 모드에서 성공/실패 구별이 유지되는지 |
| 성능 | 대표 데이터와 최대 계획량에서 메뉴 열기/스크롤/전환을 profiler로 비교. 측정 환경·데이터량·소요 시간·프레임/메모리·목표 예산 기록. 가상 목록/캐시는 병목 확인 후 도입. |

전체 조합의 곱을 무조건 시험하지 않는다. 화면별 대표 조합과 고위험 조합(확대+긴 문자열, 모달+장치 전환, 삭제+포커스)을 정하고 선택 근거를 남긴다. 미정 지원 범위와 미검수 항목은 완료 처리하지 않는다.

수동 검수는 “예쁜가” 대신 “왜 실행 불가인지 알아내기”, “선택했다가 원래 상태로 돌아오기”, “설정 변경 후 플레이 복귀” 같은 과제로 진행한다. 과제별 성공/실패, 첫 유효 행동까지 시간, 오조작·되돌아감·도움 필요 여부를 기록한다. 지식 퍼즐에서는 해답을 모르는 것과 UI를 조작할 수 없는 것을 구분한다.

증거 행: `화면/상태 | 입력 장치 | viewport/배율/문자열 | 기대 행동 | 실제 결과 | 자동 테스트 또는 캡처/측정 경로 | 통과/실패/미검수/비대상(근거)`.
